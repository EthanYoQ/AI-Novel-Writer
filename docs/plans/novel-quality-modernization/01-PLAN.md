# 小说写作质量与 Vela 退出计划

版本：v2，2026-09-12。状态：首轮阻断项已修订，待原独立审计者复审；尚不代表已批准实施。

本文件为主计划；[03-CONTRACTS-AND-GATES.md](03-CONTRACTS-AND-GATES.md) 与 [04-EXECUTION-MATRIX.md](04-EXECUTION-MATRIX.md) 是本版本的约束性组成部分，分别细化不可绕过的契约/验收与所有权/依赖。审计回执单独记录版本及哈希；通过后不回改受审正文。

## 1. 目标、范围、授权

用户要求：Vela 残留全量改写、无效残留清理，同时完成此前建议的架构调整；首要产品目标仍是小说写作质量。本轮只交付计划、独立审计和审计通过后的 Sol/high 实施 Spec，不修改生产代码，不创建 GitHub Issue/PR，不合并、不发布、不打 tag、不关闭 Issue。

“全量改写”的可验收定义：

1. 桌面生产代码不再依赖 Vela 命名的运行 API、虚拟 URI、路径散落常量或旧无效模块；新接口、新写入、新项目使用 AI Novel 的规范命名与格式。
2. 逐项登记仍被实际消费的旧实现；需要保留的能力按项目领域契约重写/收敛，不以单纯替换名字冒充架构改造，也不重写无关且稳定的第三方框架。
3. 旧格式只在集中、只读的 legacy 导入/升级边界及其测试中出现；正常业务不得继续写旧格式。旧项目经过明确告知、备份、验证和切换后使用新格式。
4. 保留历史文档、许可证、必要归属、迁移 fixture 中的历史字样；不修改用户正文中的“Vela”，不删除全局旧目录中不属于本产品的数据。零字符串匹配不是完成标准。
5. DSH 的源码、包、数据、测试与发布全部排除。保留 Electron、React、CodeMirror、Provider 适配能力、SQLite 事务、定稿快照/outbox、安全文件能力与项目会话保护。

本计划不是 clean-room 权属重建，也不宣称删除名字能改变许可义务。不能确认上游来源时如实登记，不阻止已有许可下的必要工程整理，不删除现有 LICENSE。

## 3. 成功不是“图变漂亮”，而是可检验的作者体验

### 必须改善

- 用户设定的本章人物、行动、持有物、知情状态、时间和字数范围得到落实；未来计划不被提前当作已发生事实。
- 生成过的可见内容能保存为候选并恢复；候选不污染正式成果。
- 大纲按选定范围和剩余范围生成，不一次要求模型吐出整本大结构，也不重写已成功部分。
- 改名、别名、重新生成、导入与蓝图同步不静默复制人物；模型提议不自动成为作者确认事实。
- 接受修稿对应真实正文变化；“没有产生修改”“提交成功”“意见已解决”分别表达，不要求普通作者把模型审到全绿。
- 同一生产入口的日志能区分内部预算、输入预检、供应商 length、网络、源稿冲突和存储失败。

### 不能以此换取表面成功

不得通过删除作者规则、机械截断正文、略过本章事件、放宽解析后乱写事实、自动接受新角色、取消安全边界、无限重试、换更强模型掩盖问题或隐藏错误来过验收。

## 4. 目标模块与关键契约

### 4.1 统一命名与可逆迁移

拟定规范名：`window.aiNovelAPI`、内部资源 `ai-novel://`、项目元数据 `.ai-novel/`、项目数据库 `project.db`、全局应用资料 `app.getPath('appData')/ai-novel-writer`。安装 appId 继续使用 `com.ai-novel-writer.app`，不为改名创建另一款安装应用。

先建立 typed resource parser 与 storage locator；生产调用方不允许自行字符串拼接。历史 `vela://`、`window.velaAPI` 与旧磁盘格式的适配只存在于显式兼容模块，带消费者清单及退出条件；规范写入只有一处。普通文件写入不得绕过角色/架构/草稿领域提交。

项目与全局配置迁移分别实施：

1. 只读探测旧清单、无清单旧 DB、现有新格式、混合/中断状态；不打开即写。
2. 停止本产品同项目工作流，取得有效项目身份和排他写入权；拒绝仍被旧程序使用的来源。
3. 用 SQLite backup/一致性快照处理 WAL，关闭向量库句柄；只复制允许清单内的桌面资料。API Key 不进入日志/receipt/测试仓库。
4. 在目标同卷暂存目录建新格式，验证 schema、条目数量、正文/作者事实/ID/定稿/outbox 摘要哈希及配置映射；检索索引可重建但不能丢原始资料。
5. 单一迁移 journal 推进 `prepared → verified → legacy-isolated → target-installed → switched`；每次恢复先按物理布局与指纹裁决，再开放业务，详见契约 C08。
6. 切换必须移走旧版可发现的 `.vela/project.json`、`.vela/vela.db` 所在目录，隔离备份不作为普通项目根。旧版重开无法写入原根是启用迁移的硬门槛；无法证明的历史版本只支持明确的独立副本导入，不能宣称安全原地升级。
7. 未越过隔离点的失败保留原来源；隔离后的崩溃由 journal 收敛到单一写根，不承诺每个中间态都能直接用旧版打开。已产生新写入不得原地回退旧快照；显式旧版副本使用新 projectId，并记录来源身份及不能包含的变更。
8. 全局 `.vela` 可能包含别的应用资料：只迁移本产品有证据的配置项，绝不整体删/搬用户主目录中的 `.vela`。新配置优先；双方同 ID 不同内容时要求明确选择，不静默覆盖模型或密钥。

旧适配代码退出条件：所有生产消费者已迁移，支持的历史项目经导入/升级测试，兼容 literal 仅保留在 importer、fixture、历史/许可文件中；不是简单按一个日期删除。

全局迁移必须先于所有可写消费者启动；旧源/新目标分别注入，不能让测试漏写真实 appData。模型与默认配置作为同一 generation 提交。项目 schema 有一条独占、单调版本序列；probe、schema migration、session fencing 分开。LanceDB 的 canonical chunks/documents 是不可丢的全文资料，只有向量代际可在保留文本后重建。逐类资产和 reparse-point 规则见 C08/C09。

### 4.2 生成运行：一个持久所有者，多个小型任务执行器

复用现有 generation runtime、模型租约、recovery candidate、batch 与 import ledger，不建立微服务或通用分布式调度系统。

主进程应用服务拥有运行/attempt 的预算、持久进度、取消和终态。renderer 工作流只定义任务、呈现进度、请求执行，不再另自裁决同一 attempt 终态。第一阶段保持既有任务编排，逐入口接入，不要求一次迁走所有 UI 业务。

最小对象：

- `RunRef`：projectId + rootActionId + session/epoch + runId + parentRunId（如有）+ task scope + frozen source references；rootActionId 由主进程持久创建，不随 renderer 重启重置。
- `AttemptReceipt`：attemptId、真正发送的参数、能力来源、输入估计、请求预留、实际 usage/未知、结束原因、重试原因。
- `ArtifactRef`：type、source fingerprint、range/item keys、content revision、durable offset、状态 `partial/candidate/validated/accepted`。
- 运行状态独立于成果状态：`running/paused/completed/failed/cancelled` 不替代成果是否已保存/采用。

同一次作者操作中的修复、续写、拆批及 Agent 启动的子任务使用同一父预算所有者，不能通过新开 session 重置额度。独立用户动作可有新预算，但必须复用已完成成果，不能重复提交。取消只有一个终态提交者；owner/epoch 与服务端有效期保留，客户端 expiresAt 不再作为内容写入权限的第二真相。

持久保存：只保存用户可见生成内容，不记录原始 reasoning。分块限频写入（最多约 1 秒或 4 KiB 一批），正常结束/取消强制 flush。UI 区分流式可见与已持久保存；突然断电最多损失尚未确认的尾缓冲，不能声称零丢失。磁盘满/权限失败时停止新增请求，保留可复制的内存文本并明确“尚未保存”。

采用 C02 的单 owner 规范可见前缀与 expectedRevision 单调快照，不另造分布式日志；重复/乱序写入拒绝或幂等返回，不跨 attempt 拼接。隔离结构化残片可作为用户可查看/复制/删除的候选保存，但不能作为已验证条目。

结构化输出只有完整、验证通过的条目可提交正式批次；未闭合 JSON 留在隔离候选。恢复按覆盖键继续，必须去重；源设定、模板、Skill、模型策略或正式内容变化后只保留冲突候选，不自动覆盖。

### 4.3 预算与任务分解

把内容目标、模型物理能力、执行预算和输入选择分开。保持有限的次数、时间和总额度，但 8K/4K 不再是所有任务不可变的最高值。

- 实际上限不超过用户设置、已知模型能力、剩余上下文和父任务安全额度；“用户设置很大”不等于已验证模型支持。
- 基于阶段、字段/章节数量及中文体积估计选初始批量，预计放不下时先拆，而不是先失败再无限重试。单项也放不下时分段产生候选，不删作者约束。
- 输入、输出及协议定义的独立 reasoning 开销共同受父预算约束；reasoning 已包含在 completion/total 中时不能重复相加。原子 reserve 后才可 dispatch；可信 usage 结算、未知结果保守占用，详见 C01。
- 每个物理请求只计一次；语法修复、重试、工具循环和拆批都记账。保留静态全局硬保护，不能只靠价格估计控制费用。
- 字数采用现有 `src/shared/draft-units.ts` 口径及用户目标 ±20%，不新增独立“至少 1120 字”门槛；字数合格仍要有事件覆盖，不能截到目标长度假装完成。
- 输入估计不是精确 tokenizer：记录方法/置信度/安全余量，优先用可用的协议证据与真实 usage 校准；不能再次以粗糙字符比例设一个比任务需求还小的输出硬帽。

### 4.4 一套有来源的章节上下文，不是第二套小说真相

在现有 chapter-materials、prompt-builder、continuity repository 上统一共享服务，写稿、审稿、修稿调用同一套材料选择/证据语义。

- 作者资料、正式稿和计划原文完整保存；新的 `SourceRef` 只引用现有事实源的 ID/revision/hash/offset，不复制出另一套可写真相库。
- 本章明确事件/用户指导、参与角色、必须遵守的全局规则优先；相关世界观、定稿证据、符合 C03 白名单的前章候选和参考文本分层选择。
- 不把未来计划当历史；不把模型摘要当作者事实；不把剧情树注入正文；Skill 按阶段冻结且不压过事实/结构契约。
- 派生摘要只作 locator，回读可验证的作者/定稿片段；stale 投影不作为事实。资料的 unknown/legacy 来源不自动升格为 author。
- 生成 `ContextSnapshot`：冻结源引用、纳入/省略原因、必需覆盖、token/byte 估计，不把正文写入公共日志。
- 必需资料不能容纳时优先拆当前任务；仍无法容纳则明确“本章必须遵守的资料超过当前容量”，提供缩小任务或作者选择。不能承诺任意长设定可无损塞入，也不能默默截掉尾部。
- 不引入自动全书模型重抽取；索引重建不覆盖原文，也不自动付费。

### 4.5 角色身份与事实来源

保留一个角色事实库。引入不可变 `character_id`；显示名、别名、旧 name key 映射分离。为角色静态资料补 author/derived/legacy 与来源引用；沿用动态字段的 provenance 和定稿收据。

迁移逐条给现有角色分配稳定 ID 并保持旧关联；不能因相似名字自动合并两个人。关系、蓝图、新角色候选、连续性与 Agent 工具逐入口改用 ID，显示名可改且不破坏历史。

name/alias 解析必须为 resolved/ambiguous/unresolved 三态；冲突保留原字符串与证据，不 first-match。别名作用域、历史显示快照、关联事务及显式生成/导入中的作者批准语义见 C04。

`newCharacterCandidates`、规划资料提取、导入推断统一为 proposal；只有作者在现有候选/蓝图采用界面批量确认后才能晋升。不是禁止小说引入新人物，也不增加逐人弹窗。未知角色出现在正文或旧项目中时保留证据并提示确认，不抹除正文、不默认生成角色卡。

### 4.6 审稿闭环

沿用冻结源稿、revision repository 原子合并与人工确认快照。新建小型 ReviewCycle 契约，而非通用状态平台：source hash、finding key/证据位置/类别、作者选择、revision hash、merged hash、处理状态。

- 完全相同/仅不可见格式改变不能作为“已解决”；显示“没有产生实质修改”，不自动反复调用。
- 真实合并只表示文本已提交。选中的意见再按对应证据复核，区分 resolved/unresolved/author-waived；未选意见不能伪标已解决。
- 客观矛盾与风格建议分开；同稿本同证据的重复意见合并呈现，稿本/证据变化后可重评，不永久压制问题。
- 复核预算与原任务共用，自动复核最多一次；未解决也不自动进入无限修稿。默认作者可以保留建议，不强制全绿。

finding 绑定源稿哈希、明确单位的位置/occurrence 与 excerpt 哈希；输出后和人工合并后均检测 no-op。证据 hunk 未改变不调用模型来“判绿”；新证据无法定位为 unknown/unresolved，详见 C05。

### 4.7 无效残留与重复状态清理

CodeGraph 与真实生产入口确认无消费者后，删除旧 MonacoDiffViewer、DiffViewer、无消费者 CSS/常量，以及相应依赖/锁文件/仅存在性测试；不删活跃 ThreeWayMerge 或整个 CSS 文件。

导入完成以真实 effect/operation ledger 为权威；旧 completed_batches、进度与取消字段只在完成等价对照及迁移后删除/派生。旧分布式式防御只在证明重复后收敛，保留真实外部边界。测试按根因和生产入口保留，不用测试行数决定删减。

## 6. 质量验证与发布边界
