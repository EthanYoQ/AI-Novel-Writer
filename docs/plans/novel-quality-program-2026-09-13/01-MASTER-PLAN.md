# Program v2：整合总计划

## 1. 目标与不扩展范围

最终产品目标仍是小说写作质量：长任务不浪费已生成内容、上下文有依据、角色身份稳定、审稿意见确实落实。Vela 退出与写手界面为这个目标服务，不以改名量、Issue 清零或新UI面积衡量成功。

纳入：旧24个Spec；10个开放Issue的事实清点/承接/关闭；贡献者新外壳、编辑体验、关系图及头像等实际增量；经典保留、写手默认资格、桌面发布流程。DSH、云存档实现(#213)、全新通用Agent/皮肤插件平台、英文产品场景测试均排除。

本轮授权边界：编写并独立审计整合计划/Spec。后续实施由 Sol/high 切片开发、主集成者接线与验收；远端写入和发布按对应执行阶段授权，不因阅读文档自动发生。

## 2. 主要裁决

| 议题 | 决定 | 原因/约束 |
| --- | --- | --- |
| 前端是否换语言 | 不换；移植现成React/TS/CSS到最新生产树 | index.html只是入口；不加载任意HTML/脚本作为皮肤，不保留两个业务后端 |
| 是否直接复制贡献者整个工程 | 否，按差异清单逐项接入 | 贡献目录不是最新master替代品；1.1.0以后修复和独立交互改动须合并审查 |
| 外观组织 | 外壳“经典/写手”；颜色与背景作为从属外观设置 | 原SkinId的classic表示无背景图，不等于旧UI；避免两个“经典”互相覆盖 |
| 默认策略 | 全部功能门通过后，新安装/无明确外壳偏好使用写手 | 旧版首次升级到写手可回经典；已有明确v1/v2选择、颜色/背景/字体选择不强改 |
| “全量Vela” | 清除生产旧实现与写接口，不删除版权历史、隔离导入或作者文字 | 新界面新增旧前缀/头像/缓存也进退出表 |
| Issue基本关闭 | 先已完成3项，再将有完整承接的旧项归档；未承接项保留 | 不用缺日志/旧日期证明用户不会用或已修复，不把关闭率当质量指标 |
| #213云存档 | 保留长期路线Issue，本计划不实现 | 与本地迁移/外观质量非同一范围 |
| 是否增加模型测试规模 | 不增加总帽；沿用80次总物理调用与18章最终对照 | 皮肤等价先用无模型fixture；不按每个颜色重复真实生成 |

默认策略是本计划显式产品决定，不把旧软件“没有外壳字段”等同作者明确选了经典。旧字段 theme/skin/font 原值完整迁移；只在缺外壳选择时采用新默认。默认切换不会改小说、模型、采样参数或生成策略。

## 3. 波次、顺序与并行

1. **W0 取证与承接准备**：S00复核最新master、工作区/贡献者manifest、Issue更新、生产入口与可执行旧基线。S01固定契约及共享owner，F01固定外观偏好兼容。G01关闭已有完成证据的条目，建立完整canonical承接后才归档旧追踪；不做自动批量关单脚本。
2. **W1 接口/存储基础**：S02→S03→S04。F01成果供S03全局迁移；F02只移植独占外壳/CSS资产，可在S02后与迁移并行，不抢业务页面。新增头像/正文尾句缓存资产提前进入S00/S04清单，不能到最后才发现原件丢失。
3. **W2 写作内核**：S05→S06A/B/C/D→S07；角色线S08→S09A/B/C在不抢文件时并行；S10A/B→S11→S12收敛上下文、审稿及导入。按原三道早期中文门及时检查，不等所有UI完成才发现小说质量退化。
4. **W3 写手接入**：F03规范头像/相关展示资产；F04在S12后一次接入业务页面、图谱/编辑/设置增量。复用S06/S09/S11的最终组件与服务，不从贡献者版本覆盖回旧逻辑。
5. **W4 等价与退出**：F05先做两外壳Preflight准入，主集成者据receipt激活Writer发布默认（不写成作者显式选择），再在这个集成SHA完成Final验收与三道post-UI早期小场景双臂复验；原S07/S10B/S11 owner各自负责，仍计原80次总帽，S00预留。S13强依赖这些新receipt，不能吃F04前旧PASS。随后S13清除新旧全部生产Vela残留、无消费者代码/限定依赖。S14A核验已激活默认、集成测试与独立code-review、工具/版本收口，再冻结subjectSha。若此后改到入口/参数/相关实现，先按同一门重新资格，不把过期证据带入冻结。
6. **W5 产品与发布资格**：S14B最终中文质量对照；S14C实际旧版升级/重开/故障恢复；两者独立数据根、同subjectSha，可并行。S14D同SHA Windows x64/macOS arm64/macOS x64资格，不等于已发布。
7. **W6 对外交付与收敛**：R01按新授权发布已验证产物、双语非技术功能说明；G02核实实际公开Release/包含SHA后关闭已经满足产品完成门的canonical Issue。未完成/条件不足项继续open并明确阻塞。

每次最多2个不抢文件的开发Agent；schema/中心接线永远一个owner。提前可并行的是证据整理/外壳独占资产，不是同时改App、数据库、角色页面和发布配置。

## 4. 关键路径与工作量判断

关键路径仍是安全迁移→运行/恢复→预算/角色→上下文→审稿→最终质量，不是HTML转换。新UI带来编辑器行为、头像持久化、跨项目状态，属于中等规模接入，不能按“改默认值”估工时。F02可早做；F03/F04/F05必须等业务接缝稳定。

不预报未经分片测算的小时数。S00按实际差异给每片小/中/大及阻断，超大片只在无独立验收切口时保留；出现新服务/全量复写必须回主集成者拆分并补审。已在最新入口修好的问题以当前SHA复验后跳过。

## 5. 完成标准分别报告

- 审查覆盖：最新基线和贡献者差异逐文件处置，关键消费路径逐行；明确未审范围，不把CodeGraph索引或hash相同当全仓逐行审查。
- 代码修复：相关测试、生产接线、独立review无阻断，实际提交SHA。
- 产品场景：中文正文/大纲恢复/角色/审修、经典与写手关键动作分别有证据；无测试不得写PASS。
- 发布资格：三个目标、旧版升级、同subjectSha、实际安装运行；缺平台则该平台not-qualified。
- 发布/Issue：published与qualified分开；行政归档、代码完成、产品修复、已发布分别计数。

## 6. 不可用的捷径

不能把旧PR的绿色测试算新默认通过；不能把贡献者“功能全保留”文字当证据；不能靠重新降低输出帽压缩上下文；不能用更漂亮的新皮肤掩盖保存/恢复缺失；不能用Issue关闭消除待修工作。CodeGraph根/SHA失配时回当前源码，不能自动初始化或重新clone。
