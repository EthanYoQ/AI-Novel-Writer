# G01 — Issue首轮收敛和无损承接

依赖S00、S01。目标是减少失去状态的旧追踪，不是消灭未修问题。独占issue disposition表、公开说明草稿与执行回执；不改代码、不由worker直接远端写入。

1. 读取当前open Issue（排除PR）、全部新评论、label、关联PR/check/release，记录updatedAt和证据URL；快照10项只是起点。
2. 按本包03先处理#199/#205/#211；#211写清代码已合并、v1.1.0不含。出现新反例立即撤销关闭建议。
3. 对其余六个本轮范围Issue按症状映射到原/新Spec，优先原Issue作为canonical。若原Issue范围过杂要归档，先建/复用完整open successor，每个症状有owner、验收和双向链接；未准备好的实施Issue不得ready-for-agent。
4. #191明确承接导入与随剧情提议更新两部分；#221同时承接多余角色和重复正文；#187不能只用#229取代全部工作流；#224列双入口和CI当前状态；#222与PR#223只有一个owner。
5. 缺信息按03具体请求规则；本轮初始eligible为0，不凭needs-triage/日期直接关闭。#213长期云存档保留，不另做云存档。
6. #187/#219/#221/#224后继必须是持续open的产品canonical，继承G02发布门；代码child可完成但不替代产品canonical，PR用Refs而非Fixes/Closes。#187显式保留review-chapter、chapter-blueprint-directory、compact-single和v1.1.0后复现。产品canonical关闭/删除/缩scope之前先确认完整open新后继并双向链接，或先reopen原Issue；API非原子，中途失败保留open追踪。
7. 主线程获准执行后逐条fresh-read→核对→comment→close→回读state/stateReason/comment URL。失败中途记录已做/未做，不重复发相同评论；后继提前关闭/不存在时台账blocked，先reopen/re-home，不等G02才补救。用“原单归档+child关闭+未发布”台账fixture验证仍有产品canonical open，否则拒绝归档。closureCategory与releaseStatus不允许行政移交同时宣称fixed。

验收：每个旧症状恰好有可追踪主owner，零遗漏、零虚假“已修复”；缺信息有请求URL/字段/截止日；每项的closureCategory与releaseStatus分开。用只读gh issue view/api回查；无需新增机器人或单测框架。

回退：行政关闭可reopen，保留原评论，不删除反馈；公开说明有误应透明更正。交付status可是“3可关+6待承接+1长期”，不能因数量不够强关。

## 执行合同

模型：Sol/high。你不是唯一开发者，不回滚他人修改，禁止再开子代理。只改本片独占文件；共享区仅交一个接线请求给主集成者。先读本包01/04/05、旧通用执行合同及依赖Spec。源路径以开工实际工作树为准；拟新增文件必须登记。状态NOT STARTED，下面是要执行的检查，不是已通过证据。完成给出依赖/最终SHA、实际命令/退出码、证据/未执行项；密钥/作者原稿/本地路径不上传。DSH排除、产品场景仅中文。
