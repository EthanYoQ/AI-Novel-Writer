# 已定稿章节通过重开稿替换

2026-11-03，#516 第 2、3 块。设计经只读探查、三份候选设计和三路审查裁决后定稿。本批不改 schema。

## 背景

定稿后正文只读。作者发现前面某一章要改时，之前只有两条路：删掉整章重写，或者在旧版本里绕过守卫再定稿一份，留下同章多行定稿。

#526 加了 `superseded` 状态：定稿提交在事务里把同章原来的定稿降为 `superseded`，每章至多一行 `finalized`。但作者从哪里开始改、替换后旧的实体稿和知识库文档由谁清理、后面各章怎么办，还没有入口和规则。

## 决定

1. **重开是替换定稿的唯一入口。**
   - 「重新打开修改」把本章当前权威定稿复制成一份新的工作稿（`source='rewrite'`），在它的 `source_dependencies` 里记一条指向这份定稿的依赖，这条依赖就是重开关系。有发布收据的定稿记 `finalized`，带 finalizationId 和正文哈希；没有收据的旧定稿记 `legacy-finalized`，正文取 `contents.body`。
   - 定稿章的「回退到此版本」也走重开，以所选那一稿的正文作为重开稿的初始内容。
   - 每章至多一份打开的重开稿，已有就原样返回它。「打开」指：还在写、审、改，带重开关系，并且关系指向的仍是本章当前权威定稿。
   - 本章有工作流在跑时不重开（`CHAPTER_REOPEN_BUSY`）。本章属于还没写完的批量写作时也不重开（`CHAPTER_REOPEN_BATCH_UNFINISHED`）：续跑按每章最高版本核对提交收据，多出一份重开稿，这次批量写作就续不上了。
2. **只有打开的重开稿能定稿替换。**
   - 已定稿的章上，`DraftRepository.create` 拒绝新建不带重开关系的稿，`FinalizationRepository.commit` 只接受本章打开着的重开稿。定稿之前留下的旧稿、重开关系已过期的稿都以 `CHAPTER_FINALIZED_REOPEN_REQUIRED` 拒绝。界面上这类旧稿不能定稿，可以「以这一稿重新打开」。
   - 所以新定稿行上的同章依赖就是「它替换了哪一份」的唯一记录，不另存，影响提示只看它。清理步骤另按本章所有 `superseded` 行清理它们留下的投影。
   - 放弃修改就是删除重开稿。章节回到原定稿，不留任何需要清理的东西。
3. **替换在一个事务里提交，旧投影的清理是新定稿的后处理步骤。**
   - commit 把原来的定稿降为只读的 `superseded`，写入新定稿与收据。旧定稿的正文快照和收据不变（ADR-0003 修订）。
   - 新实体稿按现有碰撞后缀发布，不覆盖任何文件。
   - 新定稿的后处理依次是 `kb_import`、`chapter_notes`、`character_cards`、`remove_replaced_knowledge`、`remove_replaced_manuscripts`。两个删除步骤非关键，失败一般可以重试，只有作者改过的知识库副本例外（见下）。它们排在最后，因为批量写作和作者原稿导入的后处理遇到失败就停，清理失败不能挡住章节要点与角色状态：
     - 旧知识库文档在新文档导入之后才删。删前比对内容哈希，作者改过的副本只提示不删；重试结果也一样，不提供重试（错误表登记为 `retry: 'never'`）。
     - 旧实体稿只在内容等于旧定稿快照时删，作者手改过的保留并提示。Windows 上文件被占用时用 `retryWhileWindowsFileBusy`（`electron/utils/windows-file-busy-retry.ts`）重试，仍占用就保留并提示，可以重试。
   - 遗留同章多行定稿的修复（#526）给被降级的行登记同样的两步清理。
4. **替换不推进连续性后缀水位**（ADR-0017 修订）。
   - 本章自己的派生投影绑定的是旧收据，随来源绑定失效；后续各章的派生角色状态保留，继续进写作提示。删除章节照旧推进水位（2026-11-05 起删除也不推，见 [ADR-0025](0025-chapter-trash-soft-delete-and-restore.md)）。
   - 替换后重跑 `character_cards` 时，提示词列出所有来源是被替换定稿的字段，要求模型逐项给出当前值并带证据，可以与原值相同。仍只提交模型返回的字段。
   - 字段当前由后续章的派生值拥有、且那一章的来源仍是它的权威定稿时，本章的新值不覆盖它（`later-source-owns`）；所有者的来源已不可信时照常写入。作者字段的章号大于本章时同样跳过，不出候选。
   - 「修复后处理」的入口改为：本章当前权威定稿的最新一次后处理有任一步没成功，或者从没跑过。这个条件与原来的「最大定稿章」条件取或。
5. **叙事线索确认随正文走。** 替换事务里，证据原文仍出现在新定稿里的确认改挂到新定稿。其余留在旧定稿上，不再计入线索进度，并在影响提示里列出原文。
6. **后续内容不自动改，影响交给作者。**
   - 影响每次读取时从稿件、蓝图、角色字段来源和线索确认现算，不存储。内容包括：写于这次修改之前的后续章（有正文的和只有蓝图的分开列）、状态字段来自后续章的角色、没能改挂的线索确认。
   - 后续一章是否写于修改之前：先看它的稿件依赖，引用了本章定稿、引用的又不是替换者，就算；没有引用本章的按时间，时间相同或读不出来也算；没有收据的旧定稿一律算。
   - 影响为空时不提示。遗留重复定稿的修复没有重开关系，也不提示。
   - 定稿确认框先预览同一份影响。替换后本章正文页顶部显示「第 N 章已修改」；受影响的后续章各显示一行「写于第 N 章修改之前」（只有蓝图的写「蓝图写于第 N 章修改之前」），链回本章。
   - 「知道了」按替换者的 finalizationId 记在本机，按作品分键存在 localStorage。重启后不再弹，同一章再替换一次会再弹。项目库里没有通用的键值表，要让它随作品迁移、备份或换电脑就得加 schema，本批不做。
   - AI 审稿和修稿的上下文看不到后续已定稿的正文。重开横幅写明「AI 审稿不检查与后续章节的一致性」。

## 与审查裁决的差异

裁决原本按「同章 version 小于新定稿的最新 `superseded` 行」推导新定稿替换了谁。实现改为读新定稿行上的重开关系，原因有两个：#526 时期较低版本的旧稿可以直接替换较高版本的定稿，按版本推导会认错；遗留重复定稿的修复也会产生 `superseded` 行，它们不是重开，不该出影响提示。

## 风险

- #526 时期已经发生的替换没有重开关系：不出影响提示，也没有登记清理步骤，那时留下的旧实体稿和知识库文档要作者自己处理。
- 定稿之前留下的旧稿不能再直接定稿替换，必须先以它重新打开。这是相对 #526 的行为变化。
- 「知道了」只在本机生效。
- 新定稿与旧定稿同名时，`kb_import` 按同名换掉旧文档，不比对作者有没有改过它。这是导入步骤原有的行为，删除步骤的哈希比对管不到这种情况。
