# 删除的章节进回收站，可以恢复，也可以彻底删除

2026-11-05，#564 PR3。设计见三份候选与综合（`design-recycle/synthesis.md`），维护者 2026-11-04 裁定。本 ADR 修订 ADR-0003、ADR-0011、ADR-0017 的相关条款。迁移 M07（回收站三列、`*_all` 改名与 live 视图）在 PR3a 已落地，本 PR 不改 schema。

## 背景

ADR-0011 的删除在一个事务里登记收据，再物理删掉本章定稿、被替换的旧定稿和按章号登记的后处理记录，并从本章起推连续性水位。删错了没有回头路：正文只剩实体稿文件，而它在清理里也被删了。

## 决定

1. **删除把本章行原地标为 `deleted`，不再物理删除。**
   - 本章的 `finalized` 与全部 `superseded` 在一条 UPDATE 里标为 `deleted`，`deletion_id` 记这次删除的主收据，`deleted_from_status` 记删前状态。正文、outbox、要点、线索确认都原样留下。
   - 读取一律走 live 视图，看不见被删行；被删章的正文、要点和派生物都不进写作提示。
   - 审稿、修稿不改视图，逐个入口按父稿是否在 `drafts` 视图里过滤（`LIVE_PARENT`）。改成视图会和 M03 校验的 `REFERENCES reviews(id)` 冲突。
   - 实体稿与知识库文档照旧在删除后立即清理，收据与重试不变（ADR-0011）。
   - 按章号登记的后处理改记到 `finalization:<id>`，留到彻底删除。缺口期间按章号找「最新后处理」不会找到被删的那份。
2. **删除不推连续性水位**（维护者裁定，修订 ADR-0017）。
   - 被删章自己的投影经视图排除。后面各章的要点与派生角色状态绑定的是它们自己的正文，删除不让它们变假，照常可信。
   - 后面章节可能依赖被删章的情节，这个代价写在删除确认里（PR4），由作者判断要不要改写。
   - 补写缺口章、恢复都不推水位。设计里「恢复时有条件撤回水位」（G1）随之作废。
3. **恢复有三种方式，由当前状态现算，事务内复核。**
   - 放回原位（`into-gap`）：本章此刻没有定稿。行翻回删前状态，主定稿的实体稿置为待发布，知识文档 ID 置空，最新后处理的 `kb_import` 记为 `CHAPTER_RESTORED_REPROJECTION_PENDING`，作者点「重试」重导知识库。删除时本来就没有知识库文档的（旧版章节确认过不在库里），导入步骤原样不动。要点与角色状态绑定的收据没变，水位也没动，不用重跑。
   - 作为旧版本放回（`as-history`）：本章已经重新定稿。被删的各行一律降为 `superseded`，当前定稿不动。
   - 以被删稿开新稿（`reopen-as-draft`）：被删定稿的 outbox 是便携导入冻结的，不能重发实体稿，也不能回链知识库。以它的正文开一份工作稿，回收站这一项保留。
   - 恢复请求带作者确认时看到的方式（`expectedMode`），事务里重算不一致就拒绝（`CHAPTER_RESTORE_MODE_CHANGED`）。
   - 这次删除的清理没完成时，先续跑一次清理，仍没完成就拒绝恢复（`CHAPTER_RESTORE_CLEANUP_INCOMPLETE`，带回收据）。否则留在知识库的旧文档从此没人清，还会被当成作者资料检索出来。
   - 放回原位时，实体稿原目标若已被别的文件或文件夹占用、读不了、还被另一次没清理完的删除收据占着，或收据里的目标名不合法，就换一个不撞名的目标。被收据占着的文件名即使内容相同也不复用，否则续跑那次清理会删掉放回的这份。
   - 本章属于还没写完的批量写作时拒绝放回。
   - 前两种方式删掉这次删除的收据，同一章以后才能再删（收据按 `draft_id` 唯一）。重复请求返回 `already-restored`。
4. **彻底删除物理删掉这一项的全部行、正文和后处理，收据保留。** 收据是转移历史的删除证明（见第 6 条）。单项与清空都在一个事务里；已不在回收站的列为 `alreadyGone`。
5. **`finalized` 与 `superseded` 只由 `FinalizationRepository` 写**（修订 ADR-0003）。
   - commit 替换、遗留重复定稿修复、恢复为旧版本，都调 `demoteToSuperseded`。
   - 放回原位调 `reinstateDeleted`。它在事务里检查本章前后各至多一行 `finalized`。
   - `deleted` 只由 `ChapterDeletionRepository` 写。
6. **转移历史校验认回收站行，但同样要删除凭据。**
   - 导出后才进回收站的行，正文与 outbox 还在，照常做内容校验。
   - 和彻底删除后行不在时一样，它还要有一张有效、未冻结的删除收据。
7. **删除、恢复、彻底删除在服务层串行。** 恢复后重发实体稿期间又删这一章时，删除清理排在重发之后，不会留下一个属于已删章的实体稿文件。排队的操作轮到时先核对打开的还是发起它的那部作品，换了作品就以 `PROJECT_CONTEXT_CHANGED` 拒绝，不碰另一部作品的回收站。跨过 await 之后的每次写入（清理结果、清理收尾、恢复事务、恢复后重发实体稿的发布记录）前也再核对一次；中途被拒的清理在原作品留作待续跑，重发停在待发布。
8. **删除清理只删属于这份定稿的实体稿，选新目标避开没清理完的收据。**
   - 清理按收据记的文件名删实体稿前，先比对内容是否仍是这份定稿发布出的那份（与 ADR-0024 删旧实体稿同一规则）。作者在那里放的别的文件、手改过的文件、作为旧版本放回后又被别人占用的旧文件名，一律保留；行已彻底删除、读不到快照时也保留。
   - 正常定稿、导入已定稿章节、放回原位选实体稿目标时，都避开实体稿还没清理完的删除收据占着的文件名（`ChapterDeletionRepository.reservedManuscriptTargets`），文件在不在都算占用。
9. **回收站列表逐项容错。** 一项的行或收据残缺，只把这一项列进 `damaged`，其余照常列出。

## 不做

- 恢复时回退 generation 计数器或撤回水位（G1 作废）。
- 回收站过期自动清空。彻底删除只由作者发起。

## 后果

- 回收站随作品导出与云备份一起带走（维护者默认执行）。导入后回收站各项只能以被删稿开新稿。
- 删除不再推水位，所以删除前后、恢复前后，后面各章都不必「修复后处理」。
- 新的错误码的作者文案随回收站界面（PR4）一起登记；本 PR 只登记已有界面可能显示的 `GENERATION_REVIEW_SOURCE_DELETED`。
