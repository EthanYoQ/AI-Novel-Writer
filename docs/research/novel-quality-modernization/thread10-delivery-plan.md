## 1. 改什么，保留什么

### 2026-10-02 用户追加：模型差异与软件交付

同一产品消息在不同模型配置下出现不同结果时，先核对材料和请求接线。
有证据归因于模型能力的内容失败，不再单独阻断软件交付。
用户进一步明确：上述归因必须有真实软件流程的成功证据。
直接调用 API 即使复用产品消息，也只属于开发比较。
须在同一案例中验证原生模型准入、材料、真实请求、修稿保存及正文读回。
只有替代模型在该流程通过，才能排除已验证范围内的编排问题。
不得用直连成功、模拟响应或另一模型的运行替代。
可以用 Hy4 preview 做有界诊断，不把新增模型接入设为交付前提。
新模型缺少容量或请求责任上限证据时，只限制该配置的原生准入。

历史 FAIL/UNKNOWN 和文学通过线保持原样。
未完成第 5 节批次时，明确记录“未获正式文学资格”。
不为软件交付重跑已确认的模型失败矩阵，也不宣称全部模型质量合格。
post-UI 原生技术断言、作者值保护、来源、保存恢复和三平台资格仍须完成。
软件缺陷不得归因于模型；有限成功样本不证明整个编排层没有缺陷。
S14D 和 R01 可按此区分汇合技术资格与模型限制，发布说明须披露文学资格状态。
本节取代下文以文学批次达标为软件交付前提的冲突要求。

| 原安排 | 本次取代 |
| --- | --- |
| 一轮七案全部通过，才能开始 post-UI/full | 同一冻结候选的七案跑三轮，另做三个持续项目九章；联合按第 5 节判定，不等待某轮全绿才运行其他独立部分。 |

| 修稿/定向复核缺少已有依据，反复靠提示补丁纠错 | 先修实际材料装配，复用已捕获的作者事实、前驱和目标；再缩短审稿任务描述。 |

**不改变**：V3 时尚杂志的呈现方向、原有功能覆盖、完整旧项目副本导入、作者原件保护、必要的安装包/平台资格。首稿可以失败，软件必须能自行发现问题；最终成功稿仍须符合成文标准。历史失败不改判，开发样本不填正式名额。

这次改变的是如何估计可用性，不是证明模型从此不会失误。有限且相关的样本不能证明长期成功率；零容忍项也仍会受生成随机性影响。其取舍是：允许有限可见失败，保住明确作者约束与数据边界。

## 2. 先完成两个产品切片

### A：让审稿、修稿和复核拿到应有的依据

1. 在现有共同入口补齐已捕获的相关前驱、作者事实和本章目标，复用现有来源准入和容量裁决。不要在发送时另读一份未绑定的实时材料，也不要把所有历史无界塞入提示。
2. 区分作者亲自写的修改要求与作者选择处理的 AI 意见。选择一条建议表示授权处理该问题，不表示 AI 提议的替换事实变成作者事实。修稿必须核对已有依据，不能把错误建议当命令照抄。
3. 定向复核检查原问题是否解决、改法是否冲突；全章末审继续检查新问题。只检查原 finding 的复核不代替全章审稿。
4. 在现有一次审稿内，用短证据区分正文已发生、旧事回顾、未来计划和本章目标。优先放进已有 `goalReviews.description` 等字段，不扩 JSON 根结构、不要求长篇推理、不增加独立抽取或多票调用。
5. 保留作者确认、差异合并、原稿身份和未解决状态。新事件可以合理发展，不要求每个新动作都曾在前文出现。

主要消费者为 `refine-from-review.command.ts`、`review-chapter.command.ts`、已有 review revision context 和提示构造。以实际缺口决定修改范围，不机械改所有相关文件。用已有漏检、错误替换建议及正常稿做定向验证，确认实际请求包含所需依据；不要用整套七案证明一项材料接线。

### B：自动短细纲，不增加作者操作页面

作者点写作 → 短细纲 → 正文 → 普通首审 → 有需要时一次修稿及普通末审。前两步自动连续；本轮不做细纲预览/编辑界面，不让审稿把细纲当证据。

细纲只组织原有本章目标、前驱已经完成的事、拟写的具体行动与结果、明确时点/约束和结尾状态。目标要求本章推进时，旧事复述不能冒充新进展；作者只要求维持状态时，不强造新事件。细纲不得增加作者禁令、改变原目标或把计划写成已发生事实。

- 正文实际消费短细纲；正常成功路径新增一次短模型调用，纳入原根动作的预算和实际记账。复用 `GenerateDraftCommand` 的单章/批量共同路径，不重建工作流系统。
- 复用原生生成产物和来源记录保存实际细纲及其 prompt/source 身份；它不是正式蓝图、作者指导或可供连续性派生的定稿。不新增独立细纲数据库。
- 细纲失败就显示该步骤失败，保留作品；不能静默跳过后宣称按细纲生成。旧稿审修不强制补细纲。
- **正文已开始后的恢复必须使用原细纲及原组合提示身份。** 不允许重新生成另一份计划后继续旧正文。正文尚未开始时优先复用有效产物；既有机制确实不能复用时，可在原预算内显式重做一次，记录原产物及原因，不能静默无限重付费。
- 当前代码只对旧 reconciliation 等产物有特定恢复处理，不能假定新增用途自动可恢复。仅补新步骤所需的来源、产物和恢复分支；不做通用恢复重构，也不以赶进度为由丢弃已开始正文的身份保护。

该切片按中等改造安排，主要成本在生产生成路径及实验接线，不是界面。若需要新页面、第二套状态库或重写编排器，先缩实现方案，不把整个项目扩大。

## 3. 小批比较模型，选完就结束

### 怎么比

先用当前产品 builder 冻结同一份真实审稿消息，比较 Flash、已接好的 Pro 和用户提名的 Qwen3.8-27B；名称和可用性以执行时账户模型列表及供应商资料为准。Hy4-preview 保留为可选诊断项，本轮默认不增加第四完整测试臂，也不把预览型号设为交付默认。

这里选择的是本轮资格及推荐配置，不强改作者已有模型设置，也不增加内置托管模型依赖。

选已有六组固定材料中的五组审稿用例：两组真实问题及三组正常/误报对照；原修稿用例单独验证。调用前在开发记录列明固定原件、输入、预期行为和用途，不给模型看 oracle 或历史 FAIL 标签。

- 初批五组 × 三模型 × 两次，共 **30 次审稿用例执行**；选定候选后，对已有修稿用例再验证两次。它们是开发比较，不是正式通过率；物理调用数、耗时和使用量另行记录。
- 为公平隔离产品准入差异，筛选均可直接 API 调用同一批产品消息；实际 adapter 参数、输出上限及供应商支持的推理配置逐项记录。不得复制另一套提示组装或关闭生产预算保护。没有发思考参数只能记“未显式配置”，没有服务端证据不能宣称实际未思考。
- 直连脚本有显式请求/输出/时间边界并逐次保存请求状态，凭据走现有安全读取，不写进日志。它只写独立开发日志，不能手写唯一正式物理账本。开发日志不是第二份正式资格账本，调用汇总进入唯一检查点。
- 原生接线检查和正式实验仍由现有 runner 写唯一正式物理账本，先登记合法 phase/milestone/操作；不能借已经关闭的 diagnostic 配额或虚构一个当前校验器不认识的 milestone。

### 怎么选

只输出一张简表：模型、用例两次结果、漏检/误报、修稿是否引入问题、等待时间、请求数和原件链接。确定性检查负责格式及引用定位，简短独立评审负责语义；不以出现某个词直接裁定时间矛盾。

1. 有稳定产品接线错误，先修共同入口并只测受影响格子，不扩矩阵。
2. 优先在已接通的 Flash/Pro 中选质量可用且等待、成本可接受的一套配置。结果接近就结束比较，不为模型排名继续抽样。
3. Qwen 只有在问题稿、正常稿两类都提供明确实用收益时才进入正式接入切片：核实容量、推理参数映射和请求责任上限算法，并过原生入口检查。不能仅改名称或套用 DeepSeek 的上限假设。实际工作量由接口证据判断，不能宣称必然与 Pro 等量。
4. 确实有一个决定性格子尚不清楚，可补至总计五次，原两次也计入；不全表扩样。任何进一步比较都要说明它解决哪个具体未决选择。

优先复用现有角色配置，不为本次比较增加动态模型路由。正式冻结须写明所有实际生成/审稿/修稿角色的配置。直连效果不能替代产品准入或真实接线证据。

## 4. 实验接线只做这组必要调整

由一个 harness owner 负责 `protocol.json`、runner、driver、production fixture 及其直接消费者；产品 owner 提供新操作和来源接口，避免多人同时改同一份登记。

| 已核实的限制 | 必需改动 |
| --- | --- |
| 冻结/dry-run、full/post-UI 调度与裁决强制双臂 | 加入明确的新 candidate-only revision，按实际 arms 验目标与来源；不运行旧臂后忽略结果。历史双臂规则只解释原实验。 |
| candidate 的 full/post-UI 模板由 baseline 先导出 | 改为候选自己的真实生产模板来源并冻结，不能只删除 `TWO_ARMS_REQUIRED`。 |
| full 准备六个项目，交替跑两臂 | 改为原三个场景各一个持续项目、各三章，保留原案例材料与生产规划；项目只准备一次，不循环重建单章。 |
| 新细纲增加物理操作 | 同步实际 operation、purpose、来源、上下文与根预算消费；按真实格式修复/续写分支登记，不能写死最理想请求数。 |
| 正式 C16–C18 可重复 invocation，但没有三轮采样归属 | 在现有记录中绑定 batch、round、slot 和实际 invocation；明确重启只接未完成位置，同轮已发送的槽位不能暗中重抽。不新建调度平台。 |
| 技术 passed 容易被当成文学通过 | 技术完成、当前问题状态和独立语义判分分别记录；聚合规则按第 5 节执行。 |

现有 `selectedCandidateDrafts` 已能消费生产 IPC 回读的上一章 `result.saved`，该稿可为 `draft/revised`。连续写作无需伪定稿或放宽仓库保存保护。预登记“模拟作者选择保留问题继续”，留存当前正文与问题状态即可；缺少有效已保存前驱时不得伪造。

账本的受控追加接口会先校验新事件再写入；不合规调用不等于已经写坏总账。保留此机制、全部历史字节及失败，禁止手工拼接行。80 仍为计划额，不是全局硬帽；新调用组成与预估总量先写清，产品自己的预算边界继续有效。

**开跑前**：受影响确定性测试、零模型接线检查和一次独立切片审查完成；只补一至两条必要的原生真实接线检查，验证选定配置与新链能实际工作。已有同配置、同实现的有效检查可复用。这不是新的文学通过率门，不追加“先彩排 15 条且全绿才准正式跑”。正式命令须由实际 CLI/help 和对应协议支持，本计划不预造参数。

## 5. 正式资格：固定一批，多轮合并判定

### 5.1 分母和通过线

正式发送前固定候选代码、产品提示、模型/参数、输入、案例顺序、每条操作上限、评分口径、round/slot 与停止规则。七案三轮各用独立案例状态；连续写作另做一批三个持续项目九章。开发结果和历史 PASS 均不补位。

| 组别 | 正式数量 | 批次最低要求 |
| --- | --- | --- |
| C16 派生资料 | A/B/C × 三轮，共 9 案 | 作者值保护、来源与操作完整性 9/9；语义完成至少 8/9。唯一容错只能是次要信息遗漏或表达不足，不能遗漏原案例关键事实、写入冲突事实或覆盖作者资料。 |
| C17/C18 恢复后续写 | 四案 × 三轮，共 12 条闭环 | 成功至少 10/12。 |
| candidate 连续写作 | 三项目 × 三章，共 9 条闭环 | 成功至少 7/9。 |

**21 条写作闭环合计至少 18 条成功**，且两组下限同时满足。C16 九案另算，不能稀释写作失败。三轮不选最好一轮，也不要求任一轮七案全绿。单条 FAIL/INCONCLUSIVE 原样保留；批次允许有限失败不代表把该条改成 PASS。

### 5.2 一条闭环怎样算成功

细纲 → 首稿 → 普通首审 → 有可采纳问题时经预授权确认、一次语义修稿/合并、一次普通全章末审 → 实际保存稿。无可采纳问题时保留首稿与首审，不强造修稿。不再叠加一个同义的默认定向复核调用。

- 最终正文满足原作者事实、本章必需事件、±30%、复述/来源及自然度、人物动机、节奏可读底线。引用存在只证明可定位，不自动证明语义正确。
- 首稿有实际阻断缺陷时，首次有效 AI 审稿须提供足以行动的问题定位或目标说明；独立评审不能先告诉软件答案。偶然修对但未自主发现不算闭环成功。
- 测试预授权只选择真实 AI error/warning 及绑定当章明确必需目标、具体指出缺失/证据不足的 unknown，按报告原顺序处理；不增加 author/apply 答案、不把机械补出的 unknown 当自主发现。复用已有确认与合并边界。
- 严重误报导致无谓强制修稿、破坏原文或要求违反作者事实，计入闭环失败。无害风格偏好、合理同义表达和作者未规定的细节不升为阻断。
- 首稿表现、自主发现、误报、修稿结果、最终质量分列；首稿本已合格时，检出能力记未触发，不宣称检出率 100%。

**状态和质量是两条轴。** `receipt.status=passed`、生成完成或保存成功都不是文学 PASS。未解决状态以当前保存正文 hash 对应的终局审稿/周期为准，不能扫描旧 cycle 的所有 unresolved 后判新稿失败；也不能拿一条无关 unknown 掩盖真正漏掉的错误。

### 5.3 哪些错误不能被平均掉

- 作品丢失、作者值擅自覆盖、来源/恢复分支错误、计划冒充已发生事实进入可信派生等数据和身份缺陷：**零容忍**，不得用模型概率解释。
- 最终正文悄悄违反作者明写的硬设定：**零次**。软件正确指出并保留未解决的该类内容仍是一条失败，但不算“悄悄错”。
- 其他最终语义缺陷被漏掉或错误宣告已解决：全体 21 条中**最多一次**，该条同时计入最多三条不成功额度，不是额外额度。

“硬设定”按原作者材料预先列明来源和作用域，包括明确时间/地点/身份、禁止事项和本章必须呈现的事件；不能看完生成结果才把某条降成普通错误。前章事件的历史时点不自动等于本章时点，但当作者明确要求当章发生时必须遵守。所有事实错误仍按原标准记失败；这里仅区分整批否决与有限失败额度，不为 C17-A 等个案开例外。

上述零容忍及可达的确定性产品缺陷同时适用于交付中发现的其他有效证据。概率容错不允许忽略稳定复现的保存、材料接线或来源错误。

### 5.4 有问题的稿如何继续写

正式批次预登记模拟作者的通用选择：有真实已保存稿就保留问题标记，通过现有选稿入口继续下一章。读到的必须是本项目上一章实际保存的首稿或修后稿；不人工代写、不择优回滚、不自动 waive 或伪装已定稿。

后章仍遵守原作者硬事实，并记录前驱确有的情节；不能用前章错误覆盖作者设定。前章失败不自动判后章失败，后章若继续传播矛盾，则按本章实际输出判分。发现次数可按根因归组，但**不得据此减少 21 条分母**。

没有有效正文、来源错误或恢复不可用时，停止受影响链；后续 NOT_RUN 保留在预定分母中，不能当成功或换另一项目补位。一般语义失败不停止其他独立项目和案例。数据/账本共享故障才停止相应共享路径。

### 5.5 运行、评审和收口

- 网络/超时/无有效输出单列技术失败，同时不计成功；不悄悄排除分母。未发送槽位可继续；已发送结果未知先按既有规则对账，不能盲重发。产品已登记的格式恢复/长度续写按真实路径计数，不给夹具额外语义重试。
- 批次中不换提示、模型、案例或评分。需要产品修复时保留旧批次，修复后重新确定受影响资格；不得跨冻结批次拼成 18/21。未受影响的确定性测试和平台证据按原 SHA 与差异理由沿用。
- 两名未参与实现的独立评审各按案一次读首稿、AI 原始报告、修稿和最终稿；先形成自身的首稿判断，再核对 AI。每案只给结论、错误类型、短原文和证据位置，不把全文复制进多份 Markdown/JSON。分歧只仲裁争议项，不重审已经一致的部分。
- INCONCLUSIVE 不计成功；涉及硬设定或数据零容忍项的未决争议须解决，不能塞进普通失败额度。自动 runner 最高 pending，不能代替独立语义判断。
- **达到本批全部要求即结束文学采样**，不补第四轮证明“更稳”。不达标时输出具体产品缺陷、模型局限和缺证据三类清单，确定一个下一步；不默认再调一句提示跑全套。两轮同根因修复失败升级诊断，不是放弃修复或无限测评的授权。

## 6. 后续资格照常向交付推进

post-UI 保留预算、上下文、审稿/作者确认/保存等独有触发和接线断言，改用 candidate。只有同版本、同入口、同材料、同操作和全部断言相符，才复用正式批次证据；不相符的独有旅程执行一次。其确定性产品断言仍须通过；额外正文语义结果如实披露，不再叠一个小样本必须全绿的文学门，也不加入或替换 21 条分母。新发现的数据/作者硬约束严重问题和可复现产品缺陷照常处理。

S14B 新批次与 post-UI 接线可在自身前置满足后交错运行，不设“先七案全绿”的等待。S14C/D 的无依赖准备、审查和资格可在隔离环境推进；不能为了并行切换同一 worktree 的 native ABI。F05、完整旧项目导入、实际安装启动/恢复及三平台义务不因文学规则调整而消失。

最终汇总本候选真正完成的 Spec、剩余缺陷、证据沿用与实际包身份，完成 S14D 后按已有授权推进 R01/G02。没有发布/Issue 写授权时准备可审查产物与说明，不能伪称已发布或已结案，也不因此停掉已授权的本地开发。

## 7. 线程 10 的工作顺序与出口

1. **接管并缩范围**：只核工作树、分支/HEAD、dirty、暂停现场和唯一检查点。旧 Pro 七案登记不是待执行命令；不再跑一次来“确认旧问题”。不重新 clone、reset、clean、整体 stash 或启动旧前端调布局。
2. **并行修产品**：分配 A 材料/审稿与 B 短细纲两个 owner，共享文件预先指定唯一 writer。主线程负责集成和第 4 节 harness 接线；模型比较等相应产品提示稳定后再开始。最多两个实施 owner，留出独立审查名额，子 Agent 不再派生。
3. **一次局部闭环**：受影响测试和每个行为切片一次独审，修后只验原 finding 与受影响回归。发现重复或过度工具工作就缩到实际消费者；不叠故障矩阵，不因纯文档/辅助脚本变化重跑产品全套。
4. **选配置并接好新资格**：完成第 3 节有界筛选；真正需要新厂商时仅接胜者。集成后做必要原生检查，更新实际机器协议与操作清单，提交并冻结真实 subject。同步质量协议的“已实现/待验”状态，不伪造现成 flags。
5. **完成技术验收，单列文学资格**：先以替代模型的同案例真实软件流程成功确认模型局限，再结束该软件修复循环。补足 post-UI 原生技术断言和平台证据。声明正式文学资格时仍须完成第 5 节；未完成时记录未获资格，不以重复已知失败矩阵作为软件交付前提。
6. **交付**：软件技术条件满足后，推进剩余 S14C/D 与 R01/G02，披露模型局限和实际文学资格状态。不做可选架构、换前端、升级向量库或新评测平台。真实软件缺陷须修复，不以“再一轮看看”作为计划。

新子 Agent 默认继承主线程模型和推理强度，实际派发省略覆盖参数，不使用固定模型的角色。执行方法遵循[交付规则](../../agents/delivery.md)，允许适用的 Superpowers；不重新启动已放弃的 Codex-with-ChatGPT 配置或咨询依赖。咨询不可用不阻止本地修复，真实阻断仍须修好或如实登记。

2026-10-02 用户追加：决定停止任务前，先向“独立顾问”线程咨询停止理由、遗漏和仍可推进的工作。顾问可读取全部工作记录，不附加读取限制。同一错误连续出现两次时，可咨询方案是否正确、是否陷入重复诊断。咨询期间继续无依赖工作；顾问意见不能代替真实验收。

每次进展只更新唯一检查点：实际产品变化、已验证层次、当前阻断、唯一下一步。细纲、筛选工具、harness 各自都有上述出口；工具应服务这些出口，不再成为无限扩展的项目。
